## Task S0.1: spike scripts (agent work, own PR `feat/sandbox-s0-spike`)

**Files (tracked, no identifiers; all ids come from environment variables or arguments):**
- Create `scripts/infrastructure/sandbox_spike/app.py` — one scratch Quart/Hypercorn app with HTTP/2 enabled
  (`h2c` prior knowledge, which is what `gcloud run deploy --use-http2` makes Cloud Run speak). **Quart's defaults would fail
  item a on their own** (`MAX_CONTENT_LENGTH` 16 MiB, `BODY_TIMEOUT` and `RESPONSE_TIMEOUT` 60 s, checked on the installed
  Quart): the app sets all three explicitly (64 MiB, 300 s) and records them in each `a` row. Routes:
  - `POST /echo?down=<n>` (a): streams the request body to a file under `$SPIKE_WORKDIR`, returns `{bytes, sha256, rss_peak, cgroup_peak}`
    in a header and streams `n` deterministic bytes back (so the client can verify hash both ways).
  - `POST /recycle` (b): replies, then asks its supervisor to stop the instance. The supervisor is the spike's own
    `supervisor.py` (below): sends SIGTERM to the Hypercorn child, which finishes the in-flight response (graceful shutdown),
    then the supervisor exits 0. Replies carry `boot_id` (random per process) and `served_count`. A second request reaching
    a draining instance gets `503` with `X-Sandbox-Outcome: recycling`.
  - `GET /whoami` (e, f): returns uid/gid/groups of the server, `/proc/self/limits`, and spawns a child under a second uid
    (the image creates user `spikeengine`) reporting that child's uid, groups, applied `RLIMIT_NPROC`/`RLIMIT_NOFILE`, and a bounded
    fork attempt count; plus a write test of `$SPIKE_WORKDIR` as both uids (mode 0700 directory owned by the child's uid).
  - `GET /probe` (c): mints a token from the metadata server for the service identity and tries, **with that token only**:
    a Firestore list, a Secret Manager list, a Cloud Storage bucket list, `projects.getIamPolicy`, and one call for every API URL
    in `$SPIKE_API_PROBES` (a newline-separated file the owner writes from `gcloud services list --enabled`; see c below). Returns
    status codes only, never bodies.
  - `GET /auth-check` (e): verifies the `Authorization` bearer in-app with `google.oauth2.id_token.verify_oauth2_token`, reports
    `signature_ok`, `email_verified`, whether `aud` equals `$SPIKE_URL`, and whether the email is in `$SPIKE_ALLOWED` (a class
    only, never the address); also reports whether `X-Serverless-Authorization` was present.
  - `GET /chromium` (f): launches headless Chromium via Playwright as the engine uid with its own sandbox **enabled**, then with
    `--no-sandbox`; returns which of the two started and the error class otherwise.
  - `GET /egress` (i): tries an outbound HTTPS connection to a public host and to the metadata server; returns reachability only.
  - `GET /call?target=<url>` (e, role `SPIKE_ROLE=caller`): fetches an ID token for `target` from the metadata server and calls
    `target/auth-check`; used to test one Cloud Run service calling another.
- Create `scripts/infrastructure/sandbox_spike/supervisor.py` — the spike's recycle supervisor (the real one is S1 T5; this
  prototype is what b measures).
- Create `scripts/infrastructure/sandbox_spike/Dockerfile` — `python:3.11-slim`, `hypercorn quart httpx[http2] google-auth
  requests playwright`, Chromium, Node + the `docx` npm package at the version pinned in `docx_generator/package.json` (installed
  by name and version: the build context is the spike directory, so that file cannot be copied), user `spikeengine`, `COPY` of the
  spike directory only (never the repo root). Named `Dockerfile` because `gcloud builds submit --tag` only builds a file of that
  name (it has no `--dockerfile` flag).
- Create `scripts/infrastructure/sandbox_spike/client.py` — owner-side HTTP/2 client (`httpx`, `http2=True`) with subcommands
  `large`, `burst`, `cold`; ID token from `gcloud auth print-identity-token --impersonate-service-account=<CALLER_A_SA>
  --audiences=<SPIKE_URL> --include-email` passed as an argument or in `$SPIKE_TOKEN`.
- Create `scripts/infrastructure/sandbox_spike/equivalence.py` (g) — `--dump DIR` runs every corpus file through
  `SubprocessContentExtractor` (and the chat fixtures through `convert_file_to_text`) and prints one JSON line per file to stdout:
  `{file_id, kind, status, text_len, text_sha256}` (no text); `--compare A.jsonl B.jsonl` lists differences; `--show FILE_ID` prints
  a bounded diff window for one file (run only on a mismatch, locally).
- Tests: none (spike scripts). `make check` lints `src/` only, so the PR runs `ruff check scripts/infrastructure/sandbox_spike`
  by hand and parses every script with `python -m py_compile` (a smoke check in the PR description, not a test).
- Acceptance: PR reviewed for the secrets rule (no identifier, no URL), merged by the owner.

## a. Large bodies (the design's main technical risk)

- **Deploy:** the scratch service above (HTTP/2 end to end).
- **Measure:** `python scripts/infrastructure/sandbox_spike/client.py large --url <SPIKE_URL> --up-mib 50 --down-mib 50 --runs 5`.
  Also the control: `--up-mib 33` over HTTP/1.1 (`--http1`) to confirm Cloud Run's 32 MiB limit answers 413; and 45 MiB
  (the drive cap) over HTTP/2. Record per run: status, round-trip wall, SHA-256 equal both ways, the app's `rss_peak` and the
  container cgroup peak (`memory.peak`, v1 fallback). **Note:** the workdir is an in-memory volume, so a 50 MiB upload counts
  against instance memory twice (file + any buffer); that is why RSS and cgroup are both recorded.
- **Pass:** 5/5 runs at 50 MiB up and down over HTTP/2 with equal hashes; app RSS under 150 MiB (proves streaming); cgroup peak
  under 400 MiB; the HTTP/1.1 control at 33 MiB fails with 413 (confirms the limit is what we think).
- **Fail handling (O6):** if bodies above 32 MiB fail over HTTP/2, 32 MiB becomes a documented limit for parsed files; no
  signed-URL fallback and no change of the drive cap. This changes S3, not S1; S1 only carries a `request cap` constant.
- **Results:** `scripts/memory/sandbox_spike/a_large_bodies.json`.

## b. Recycle and cold start

- **Deploy:** the scratch service, started through `supervisor.py` (the image's default command).
- **Measure:**
  1. `client.py burst --sequential 20` then `--parallel 5`, each call `POST /recycle` with a 1 MiB body and 1 MiB reply.
  2. Per call: status, whether the body was complete (hash), `boot_id` (a new value each call), `served_count` (always 1),
     whether the response carried `X-Sandbox-Outcome: recycling` (503), and whether `httpx` observed `GOAWAY` or a
     `Connection: close` (log the h2 connection-terminated event).
  3. `client.py cold --runs 10`: wait 15 minutes so no instance is warm, then time first byte of one call, 10 times with 5-minute gaps
     (or use `--max-instances` changes to force fresh instances); report p50/p95 time to first byte. The scratch image
     is smaller than the render image will be, so also time the **repo image** (built for g/h) as the upper bound, and say which
     is which.
- **Pass:** 25/25 responses complete, a distinct `503 recycling`, or a platform `429` (5 parallel calls against
  `--max-instances=3` can exhaust instances; each 429 is recorded separately — it is the `SandboxUnavailable` row of §4.9 and
  sizes `max-instances`, not a failure of the recycle); **zero** truncated or reset responses without a `recycling`
  answer; **zero** instances with `served_count` above 1; the recycling-answer rate in the parallel burst is reported (no
  threshold — it sizes the client's retry, 3 attempts per §4.9). Cold start p95 is reported; if the heavy image's p95 exceeds 8 s
  report it to the owner before S1 acceptance (O5 accepted 1-3 s; a larger number is new information).
- **Fail handling:** truncation without `recycling` means the supervisor stops the instance before the last byte is flushed; S1
  T5 then needs a flush barrier (see Gap G7) before it can be accepted.
- **Results:** `b_recycle.json` (all per-call rows) and the two cold-start tables.

**Scope (RFC §7 S1):** `src/domain/sandbox_contract.py`; `sandbox_main.py`; `src/web/sandbox_app.py`;

**Design choices the RFC leaves open, stated once so tasks can refer to them (all also in Part C):**
- `render.docx` body framing: `u32-be script_length | script bytes | spec bytes`. The server writes the body to a file and never
  splits it; the engine child splits it (G1).
- Process model: `sandbox_main.py` is both the supervisor (default) and the server (`--serve`), one file as the RFC lists (G7).
- Failure text of a script travels in the response **body** (`text/plain`, capped), the outcome header carries only the status (G2).
- The service's `render.docx` engine is a **new** `DocxRenderEngine` + child, not `NodeDocxRunner` itself as RFC §4.7/§4.10/§4.11
  name it: `NodeDocxRunner` writes into `docx_generator/`, runs `node` as the caller's uid and applies no rlimits, so it cannot meet
  §4.6. Its observable contract (error texts, prelude) is kept and pinned by the contract suite (G20).

## Task T4: server app (routes, size and header checks, one request per instance)

**Files:**
- Create `src/web/sandbox_app.py` — `create_sandbox_blueprint(engines, gate, recycler, limits_ceiling, config)` and `GET /health`.
  `POST /v1/<op>` order: (1) caller gate (401 on no/invalid token; 403 on a token that is valid but not allowed this op); (2) unknown
  op 404; (3) draining or busy -> `503` with outcome `recycling`; (4) `Content-Length` pre-check and streamed byte count against
  `REQUEST_CAP_BYTES` -> `413`; (5) decode `X-Sandbox-Meta` (closed schema, else 400 `bad_request`); (6) stream body to
  `workdir/<request_id>/body`; (7) clamp limits; (8) run the engine; (9) respond with `X-Sandbox-Outcome` always present, body =
  bytes (ok) or capped text (failure); (10) after the response is handed to the server, tell the recycler (`always`) once.
  **Which requests recycle:** every request that passed the gate and had payload bytes written (step 6, or a streamed body that
  crossed the cap midway in step 4), whatever its outcome; requests refused before any payload byte was written do not (G8).
  **Draining is visible (§4.6):** the answer to a request that will recycle carries `Connection: close`; on HTTP/2 the graceful
  shutdown of T5 sends `GOAWAY` after it. Both are asserted (header in T4, GOAWAY by S0-b).

# Part C — Gate 2 gap list (open points; nothing here is silently decided)

Each item: what the RFC says or omits, what I propose in this plan, and whether it needs the owner.

- **G1. `render.docx` request body framing is not defined.** §4.7: "raw body is the payload", metadata in a header of at most 8 KiB;
  but `render.docx` has two inputs (script text and spec JSON), and a spec can exceed 8 KiB. *Proposed:* `u32-be script_length |
  script | spec`, written to a file by the server and split by the engine child, so the server never interprets the payload.
  Engineering detail, settled here (no owner input); changing it later changes the wire format, so T1/T3 pin it with tests.
- **G2. Where the script's error text travels.** §4.9 says the op returns the error text, while the outcome header is
  base64url JSON (§4.7). Headers are size-limited and a Node stack can be long. *Proposed:* status in the header, text in the
  response body (`text/plain`, capped at `ERROR_TEXT_CAP_BYTES`, truncated with a marker). The cap is a new constant; the
  in-process runner does not truncate, so for very long stderr the two adapters differ by design (64 KiB proposed: far above
  any useful Node stack, far below the response cap). Engineering detail, settled here; the contract suite compares below the cap.
- **G3. Sharing the security prelude between the in-process runner and the sandbox engine.** REQ-ARCH-23 forbids adapter-to-adapter
  imports, and the engine is a different adapter subpackage. *Proposed:* move `_SECURITY_PRELUDE`/`_SAFE_ENV_KEYS` to
  `src/domain/docx_script_prelude.py` and re-import them under the old names in `node_docx_runner.py`. `test_node_docx_runner.py`
  imports `NodeDocxRunner`, `_DOCX_GENERATOR_DIR`, `_SECURITY_PRELUDE`, `_safe_subprocess_env` from `node_docx_runner`
  (`tests/unit/adapters/test_node_docx_runner.py:19-24`); all four stay module-level names there, so **no test is edited and no
  import path changes** — the rename exemption is not even needed. Domain may hold a pure string constant; `_safe_subprocess_env`
  stays in the adapter because it reads `os.environ` (REQ-ARCH-17). Alternative: duplicate the string (two copies drift —
  rejected). Engineering detail, settled.
- **G4. The `abnormal` recycle policy.** §4.6 says production offers only `always` ("a policy `abnormal` is not offered in
  production") but the S1 Tests bullet says "recycle (`always`, `abnormal`)". *Proposed:* tests cover `always` and `never`
  (local only) and a test that `abnormal` is a startup error. If the owner wants `abnormal` as a local-only policy (recycle only
  after a non-`ok` outcome), that is an addition. **Unmapped-as-written RFC bullet:** the `abnormal` policy cannot be tested
  as a working policy because the RFC says it is not offered.
- **G5. Node module resolution.** `NodeDocxRunner` writes the script into `docx_generator/` so `node_modules` resolves. The sandbox
  child writes into the per-request workdir (needed for uid isolation and the size-limited volume). *Proposed:* `NODE_PATH` to
  the image's `docx_generator/node_modules`. Spike S0-f runs one DOCX build to prove it; if it fails, the child needs a read-only
  bind of `node_modules` next to a per-request script.
- **G6. Memory limit mode for Node.** The RFC lists `RLIMIT_AS` 1 GiB (§11, copied from the Python parsers). V8 reserves large
  virtual ranges and may not start under a small address-space limit. *Proposed:* S0-f measures it; if 1 GiB fails, node children
  use `RLIMIT_DATA` plus `--max-old-space-size`, and §11's table gets a node row. The numbers `NPROC`/`NOFILE` are "set at S0-f"
  per §11 — the plan reads them from that result.
- **G7. "Respond, then stop" can truncate.** §4.6 relies on the supervisor stopping the instance after the response. Whether
  the last byte has left the container when Hypercorn reports the response finished is exactly what S0-b measures. *Proposed:*
  graceful SIGTERM (Hypercorn finishes the in-flight response), and a flush barrier if S0-b shows truncation. Also, the RFC lists
  one entry file (`sandbox_main.py`) but the supervisor and the server are two processes; *proposed:* one file with `--serve`.
- **G8. A rejected request must not consume the single use.** Under `always`, if any request ended the instance, an anonymous
  caller who gets the pre-gate 401/403 could burn instances (cheap denial of service). *Proposed:* the recycler fires for every
  authorized request that had payload bytes written, whatever its outcome; a request refused before any payload byte was written
  does not recycle (T4 tests). I2/I6 are about payload data, and such a request left none, so this meets O5's intent. The
  platform's IAM check already blocks unauthenticated callers before the app; this covers a mis-bound caller. Engineering detail.
- **G9. First-deploy audience.** The in-app gate pins the audience to the service's own URL (§4.4), which is unknown before the
  first deploy. *Proposed:* the indexer's two-pass pattern: start with an empty URL, answer `503 unconfigured` and serve `/health`,
  then redeploy with the URL. The RFC says "refuses to start if ... a caller set is empty on Cloud Run"; an empty URL is a
  different case and is handled as `unconfigured`, not as a refusal. On Cloud Run the URL is also derivable ahead of time
  (service name, project number, region), which would make one pass enough, but I did not assume the URL format.
- **G10. What the DocGenerator does when the sandbox is down.** §4.9 defines the chat alert for conversion only. For DOCX, the
  agent's repair loop treats `DocxRunnerError` text as a script bug and asks the model to fix it
  (`doc_generator_agent.py:211-219`); any other exception escapes `execute` today. *Proposed, following §4.9 row by row:*
  `SandboxUnavailable` and `SandboxMisconfigured` are systemic and "nothing is charged to the file" — here, to the script — so they
  are **not** `DocxRunnerError`: the agent catches them and returns `AgentResponse.failure` without another model turn (T8b; new
  tests only). `sandbox_lost` is the opposite row of §4.9 ("two losses mean the file", charged to it): for DOCX the input is the
  model's script, so it **is** a `DocxRunnerError` and the model gets its normal repair turn, bounded by `MAX_TURNS` (an earlier
  draft of this plan made it `SandboxUnavailable`, which contradicted §4.9). The user-visible wording of the systemic failure is
  the existing `AgentResponse.failure` path; no new alert (the RFC defines one only for chat conversion). Engineering, consistent
  with §4.9.
- **G11. `httpx` with HTTP/2.** `requirements.txt` declares `aiohttp` (HTTP/1.1 only) and no HTTP/2 client, but `httpx` is
  already installed and imported by six adapters (`http_call_control_plane_adapter.py`, `gemini_adapter.py`, …) as a **transitive**
  dependency of `openai`, `anthropic`, `google-genai`, `mcp`, `firebase_admin` and `python-telegram-bot` (0.28.1 in the venv), and
  `h2` is installed through `hypercorn`. §4.7 requires an HTTP/2 client for bodies above 32 MiB. *Proposed:* declare `httpx` pinned
  to the version those SDKs already resolve, and `h2` explicitly, in `requirements.txt` (so the HTTP/2 path does not hang on another
  package's dependency list). No new library enters the image. The RFC does not name the library. Engineering detail.
- **G12. Which uid the server runs as.** I7 says engines never share the server's uid, and the launcher switches uids, which
  needs privilege. The existing images stay root so the child can be switched (Dockerfile comment). *Proposed:* the sandbox
  server also runs as root **inside a container that holds nothing**, and only the engine children are dropped; the claim is
  "the process that accepts requests is not the process that touches bytes", not "the server is unprivileged". If the owner
  wants an unprivileged server, it needs `CAP_SETUID/SETGID` as file capabilities on a launcher, which adds a setuid-style
  component.
- **G13. `src/utils/logger` pulls telemetry.** Known, not "to be measured": `logger.py:4-5` imports `.telemetry` and
  `.logging_context`; `telemetry.py:5-10` imports the OpenTelemetry SDK and `CloudTraceSpanExporter` (the Cloud Trace client) at
  module load; `logger.py:87` imports `google.cloud.logging.handlers.StructuredLogHandler` when `K_SERVICE` is set; `logfire` is
  imported only inside `telemetry._init_logfire`, which only an explicit tracing init calls. None of these is Firestore, Secret
  Manager or Storage, and none exports anything unless tracing is initialised (the sandbox never does; `StructuredLogHandler`
  writes JSON to stdout, the RFC §4.3 claim). So the RFC's image-contents rule holds with the shared logger as is. *Proposed:*
  keep `from src.utils.logger import logger` (CLAUDE.md rule), put those packages in `requirements-sandbox.txt`, leave `logfire`
  out, and allow them by name in T9's closure test (the plan's own extra bans must not forbid what the logger needs). No slim
  logger, no owner decision. Cost: a few tens of MB of gRPC/OTel libraries in an image that holds no credential to use them with.
- **G14. `SandboxUnavailable` placement.** The RFC says "domain exception". Two tiny classes in one module breaks the
  one-public-class rule; I use a stated waiver (precedent exists). Alternative: two files.
- **G15. Docker-gated tests are not in CI.** `make check` has no docker. The import-closure and COPY-allowlist tests are static and
  run in CI; the "cannot import Firestore inside the image" test and the uid test run only when a daemon is present. The RFC's
  image-contents bullet is therefore **partially enforced in CI** (static) and fully only at acceptance (docker).
- **G16. Default of the switch and the Cloud Run ERROR line.** §4.12 says an unset knob is `sandbox` after acceptance and
  `inprocess` on Cloud Run logs an ERROR at start. During S1 the default is `inprocess` and the ERROR line is **not** added
  (it would fire on every boot of the live service); both arrive with the follow-up flip. This is what §4.12 already says
  ("default `inprocess` until its slice is accepted"; the ERROR sentence describes the state after acceptance). No owner input.
- **G17. Deploy order.** I place the sandbox build and deploy after the indexer steps so a sandbox failure cannot block a bot
  hotfix. But the main service step reads `SANDBOX_RENDER_URL` from `.env` before the sandbox exists on a first deploy; that is
  the two-pass note. The RFC does not specify step order.
- **G18. §4.4 startup check wording.** "Refuses to start if the caller sets of two op families overlap, or if a caller set is empty
  on Cloud Run" and "fail closed when the email map is empty" overlap. In S1 only the `render` family exists; the overlap check
  is exercised with synthetic families in tests, and an empty `render` set on Cloud Run refuses the start.
  **"Op family" must mean caller group, not op prefix.** §4.4 also gives the indexer `drive.*` **and** `media.*` on the light
  service; read per prefix, the indexer's email sits in two sets and the overlap check refuses the light service's start at S5.
  *Proposed:* a family is the set of op prefixes one runtime may call (`SANDBOX_CALLERS_INDEXER` → `drive`, `media`;
  `SANDBOX_CALLERS_MAIN` → `chat`, `render`; S1's render service: `SANDBOX_CALLERS_RENDER` → `render`), and disjointness is
  checked across groups. Keeps P0's intent (no runtime admitted through another's identity). Engineering detail.
- **G19. §12 item 6 (one image for every runtime) stays true in S1.** The main and indexer images still carry Node and
  Chromium until S6-a; S1 adds a separate image but removes nothing. Acceptance must not be read as "the main image no
  longer carries the DOCX engine".
- **G20. The service's DOCX engine is not `NodeDocxRunner`.** §4.7 ("Engine behind it: `NodeDocxRunner`"), §4.10 and §4.11 ("maps
  each op to its in-process adapter") name the existing runner as the engine. It cannot be used as is: it writes the script into
  `docx_generator/`, runs `node` under the server's uid and applies no rlimits, which breaks §4.6 (the design rule). *Proposed:*
  a new `DocxRenderEngine` + `render_docx_child` (T3) that keeps the runner's observable contract (prelude, error texts) and is
  pinned to it by the contract suite (T8). Alternative: give `NodeDocxRunner` optional uid/limits/workdir parameters so it is
  literally the engine; rejected because it would change a live adapter's code paths and contract tests
  (`tests/contracts/adapter_contracts.py` pins "script under `docx_generator/`"). Engineering detail forced by §4.6.
- **G21. The in-app gate makes one outbound call.** §4.5: "for every op except `media.*` the service makes no outbound call", and
  S6 removes every route out. But §4.4's in-app verification (`verify_oauth2_token` + `google.auth.transport.requests`) fetches
  Google's public signing keys from `www.googleapis.com` on each verification, and with `recycle=always` nothing is cached. The
  call is made by the server process (never an engine) and carries no payload. *Proposed:* state it as the one documented
  exception (T9 architecture test names it); S0-i measures whether it survives deny-all egress; if not, S6 adds Private Google
  Access plus an egress allow rule for the `private.googleapis.com` range. No S1 code change; the RFC text of §4.5/S6 gets one
  sentence when S6 is planned. Engineering detail, reported to the owner as information.
- **G22. The audit will flag the drive indexer.** RFC §8's intended public-invoker set is "the main service … and the voice
  relay, and nothing else", and S0-d's pass rule says anything else blocks S1 acceptance. `cloudbuild-dev.yaml:152-164` grants
  `allUsers` invoker on the indexer at every deploy (it sits behind `--ingress=internal` and an in-app OIDC gate with a pinned
  audience; the comment at `:141-147` explains why: Cloud Tasks' token audience is `{url}/worker`, which platform IAM would not
  accept). **Owner decision:** either (a) record the indexer as an accepted member of the set (internal ingress + in-app gate)
  and amend RFC §8, or (b) make removing it a precondition of S1 acceptance, which means reworking the indexer's task audience
  and belongs with the per-runtime identity work (P0). Nothing in S1's code depends on the answer.
- **G23. The deployer needs `actAs` on the sandbox identity.** Every current deploy runs as the default compute identity, so
  `--service-account=$_SANDBOX_RENDER_SA` is the first deploy that needs `iam.serviceAccounts.actAs` on another identity.
  *Proposed:* owner step 2a grants `roles/iam.serviceAccountUser` on `<sandbox-render-sa>` (as a resource) to the deployer only;
  the sandbox identity itself still holds nothing. Missing from the RFC §8 list; engineering detail.
- **G24. Caller lists cannot use commas.** The values ride Make → shell → Cloud Build `--substitutions` → `--set-env-vars`;
  the last two split on commas and the shell splits on `;` and spaces. *Proposed:* `:`-separated (no email contains `:`); a comma
  in the value is a loud start-up error. S1 needs one email per group anyway. Engineering detail.
- **G25. RFC §8's "empty the caller map" stop does not stop a single-family service.** With an empty set on Cloud Run the new
  revision refuses to start (§4.4), so Cloud Run keeps serving the previous revision. *Proposed:* the plan's rollback uses the
  switch first and, for a hard stop, removes the caller's invoker binding (immediate, one command). RFC §8 stays right for
  removing one family of several. Engineering detail.
