# Decision: a review pass decides what a stale fact is, and what it cannot decide is asked one question at a time (Facts S4, 2026-10-26)

**Decision.** Spec: `docs/10_rfcs/FACT_LIFECYCLE_RFC.md` D6, D7, D10, P1–P3 and "S4 as built"; owner's map: `docs/05_building_blocks/memory/README.md` §5.5, §5.6. Owner rule through all of it: **when unsure, keep the fact, and ask.**
- **The review is one more pass of the consolidation agent**, with its own profile and blueprint (`consolidation_review`, tokens `CONSOLIDATION_TAXONOMY` and `CONSOLIDATION_LIFECYCLE`), three tools (`update_fact`, `ask_owner`, `count_words`) and no search, create or merge. It runs under the account's memory-write lease, daily (`fact_review_interval_days`, default 1), only when something needs it. Code refuses a change without a reason: a revive, a rewrite or an invalidation needs another current fact or the owner's reply with a quote; an archive also accepts the passed date of a dated plan. A refused call writes nothing.
- **What it cannot decide is queued as a question, and the fact is current while it waits.** The pool (stale facts plus the facts of open questions) is bounded at 50 by the janitor's cap and breaker. A waiting fact is never hidden and never silently revived: after 14 days of silence the question's fallback applies, and a revive gives twice the window the last one gave (14 to 365 days), every time.
- **One question, one fact, one digit.** The question is written by code (never by a model), goes only to the primary chat, one at a time, at most 5 a day. The language follows the response-language setting; a language without UI strings uses model-written labels that pass code checks, else the UI language.
- **An answer is only a reply to the question message, a button click, or a Cabinet click, and one service applies it** (`FactAnswerService`: the write rules of the `owner` actor, the same preconditions as the review, no model, no lease). A reply in words is recorded and read by the review once. The reply and its acknowledgement are a pair in history under a narrowed echo-trap exception: the quoted fact belongs to the review and Stage 1 records only what the answer adds.
- **Every question closes through one method** that clears the current slot, releases the next question and re-renders a Slack message without its buttons.
- **Interactive messages are one platform-neutral model** (prompt, quote, options, binding) with adapters: Slack buttons through `/slack/interactivity` (signature checked on the raw bytes before anything is parsed, the work done in a Cloud Task), plain text with digits on Telegram. A click is routed by its binding's kind.
- **The owner sees what was set aside**: a weekly digest (literal text, only removals made by the review, a timeout or the owner) and, in the Cabinet, the stale facts, everything set aside in 30 days with its actor, and the question list. The Cabinet cannot restore a closed fact; the chat can.
- Records expire by a TTL policy on `purge_after` (closed questions and digest claims, 90 days); the state document and the janitor's run guard have none. No field is named `expires_at`.

**Rejected.**
- Questions written by the review model, several per message, answered by number: partial answers are ambiguous and model-written text can restate the fact differently from how it is stored. One fact per message needs one digit, and code quotes the fact as stored.
- Any message after the question counting as the answer: a plain "2" can be about anything. Only a reply to the question message counts.
- Recording the reply from the consolidation batch (the RFC's P1 as written): the answer would wait for a batch (hours to a day) and `ConsolidationService` would gain a second job. The intake applies it at once.
- Hiding a fact until its question is answered, or reviving it by code on silence: the first loses memory the owner never decided to lose, the second guesses; the queue keeps the fact visible and asks.
- A silent archive on silence for a lasting fact: silence is not a decision. Only a dated plan, a past `fallback_date` or noise falls back to archive.
- A separate service for the digest and a daily message claim: the review run already holds the facts; one claim per ISO week is enough.
- Letting the Cabinet restore a closed fact: left for a follow-up, because a restore needs the same preconditions and a decision about its horizon.

**Revise when** the owner asks for answers by phone call (a call note that carries an answer), a second answer path writes more than one fact and its history fact, the Cabinet gets a restore, Telegram gets inline keyboards or Smart sends interactive blocks (the port is ready), or the S5 classify shows the pool bound of 50 slowing the drain.
